Barcode & QR

Scanning is the easy half. The interesting decisions are which engine you can ship in which build channel, how to keep a camera surface testable, and what to do when the thing you need to read is a seven-segment display rather than a code.

Choosing a scanner engine

Two realistic options in Flutter, and the deciding factor is usually your distribution channels rather than accuracy.

ML Kit-backed (mobile_scanner)ZXing via FFI (flutter_zxing)
Accuracy on damaged / angled codesBetterGood
Android dependencyGoogle ML Kit → Play ServicesBundled native library, no services
Ships in a libre buildNoYes
iOSVision or ML KitSame FFI library
DesktopLimitedYes
Binary sizeSmaller if Play Services provides the modelA few MB of native library per ABI
Offline first scanMay download a modelAlways available
Rule

If you ship to any channel that forbids proprietary services, pick the libre engine for that channel — and consider picking it everywhere. One codebase with one scanner is cheaper to maintain than two. One project keeps the ML Kit engine on its store builds and swaps in the ZXing engine for the libre build; the honest assessment is that the accuracy difference did not justify the dual path, and a single ZXing path would have been simpler.

The per-channel engine swap

Swap the package at dependency-resolution time, not with a runtime branch — a runtime branch still links both libraries into the artifact.

This is the point people get wrong. Writing if (AppFlavor.isLibre) useZxing() else useMlKit() selects the engine correctly and leaves every ML Kit class in the binary, where a channel's bytecode scanner will find them. The swap must happen before the build sees the dependency.

tool/apply_fdroid_overrides.dart      # run BEFORE `pub get`
  ├─ copies pubspec_overrides.fdroid.yaml → pubspec_overrides.yaml
  │     mobile_scanner: { path: tool/fdroid_stubs/mobile_scanner }   ← no-op stub
  └─ copies pubspec.fdroid.lock → pubspec.lock                       ← libre lockfile

The stub is a package with the same public API whose methods throw or return an unavailable state. Nothing imports it directly; the real code selects the ZXing path when the flavor is libre, and the stub exists solely so the ML Kit symbols leave the dependency graph.

Rule

Maintain a second lockfile for the libre build and regenerate it on every dependency change. One project's F-Droid audit goes red on every dependency-update pull request until pubspec.fdroid.lock is regenerated by hand. Automate it or add it to the update checklist — it is a recurring cost that is trivially avoidable and reliably forgotten.

Check

Prove the swap worked by auditing the built artifact, not the dependency graph. See page 17 — a release-mode bytecode scan must report zero references, not merely zero declared dependencies.

An injectable scanner seam

A camera preview cannot run in a widget test. Put the scanner behind a widget-level seam so tests inject a fake that emits a scripted result.

/// Production embeds the real camera reader; tests inject a fake that
/// fires [onCode] on demand. Same idiom as the NFC reader seam.
typedef ScannerBuilder = Widget Function({
  required ValueChanged<String> onCode,
  required VoidCallback onCancel,
});

class QrScanWidget extends StatelessWidget {
  const QrScanWidget({super.key, required this.onCode, this.builder});

  final ValueChanged<String> onCode;

  /// Overridden in tests. Defaults to the real camera reader.
  final ScannerBuilder? builder;

  @override
  Widget build(BuildContext context) =>
      (builder ?? _realScanner)(onCode: onCode, onCancel: () => Navigator.pop(context));
}
testWidgets('scanning a workspace code joins that workspace', (tester) async {
  late ValueChanged<String> emit;
  await tester.pumpWidget(_app(
    scannerBuilder: ({required onCode, required onCancel}) {
      emit = onCode;                       // capture the callback
      return const SizedBox.shrink();      // no camera in a widget test
    },
  ));

  emit('deskilo://join?ws=abc123&t=XYZ');  // simulate a scan
  await tester.pumpAndSettle();

  expect(find.text('Joined workspace'), findsOneWidget);
});
Why a widget-level seam rather than a service

Because the thing that breaks is usually the screen, not the decoder: a scan that fires twice, a navigation that happens after the widget unmounts, a result handled while a dialog is open. Injecting at the widget boundary lets a test drive exactly those paths. The decoder itself is third-party code with its own tests; you do not need to test that ZXing can read a QR code.

Trap

Symptom: one scan produces two navigations, or a duplicate record. Scanner callbacks fire per detected frame, so a code held in view for half a second fires many times. Debounce on the decoded value and stop the scanner on first accept:

String? _last;
void _onCode(String value) {
  if (value == _last) return;
  _last = value;
  _controller.stop();          // stop BEFORE the async work
  unawaited(_handle(value));
}

Stop the controller before awaiting, not after — the frames arriving during the await are exactly the duplicates.

Generating codes

Generating a QR code on screen is a widget; the decisions that matter are error correction, quiet zone and contrast.

QrImageView(
  data: payload,
  version: QrVersions.auto,
  // M (~15% recovery) is the right default for a screen. Use H (~30%)
  // only when a logo is overlaid or the code will be printed and handled.
  errorCorrectionLevel: QrErrorCorrectLevel.M,
  size: 240,
  // The quiet zone is REQUIRED by the spec. Without it many scanners
  // simply fail, and the failure looks like a bad camera.
  padding: const EdgeInsets.all(16),
  backgroundColor: Colors.white,   // always light background
  eyeStyle: const QrEyeStyle(color: Colors.black),
)
DecisionGuidance
Error correctionM on screen; H when printed, laminated, or overlaid with a logo. Higher correction means a denser code for the same payload.
Quiet zoneNon-negotiable. At least four modules of margin. Most "the scanner does not work" reports are a missing quiet zone.
Contrast and polarityDark on light. Inverted codes are optional in the spec and many scanners skip them.
Dark modeForce a white card behind the code regardless of theme. A QR code on a dark surface scans poorly.
Screen brightnessRaise it while a code is displayed for scanning, and restore it after.
Payload sizeShorter is denser-free. Prefer an id over an embedded JSON blob — see payload design.

Printable code sheets

When codes are physical — a code per seat, per asset, per member badge — generate a PDF on-device rather than sending anything to a server.

pw.BarcodeWidget(
  barcode: pw.Barcode.qrCode(),
  data: 'app://seat?id=$seatId',
  width: 96,
  height: 96,
)

Practical requirements learned from shipping this:

  • Label every code with human-readable text. A sheet of anonymous squares is unusable when one falls off a desk. Print the seat name or asset id under each.
  • Embed a font. The PDF base-14 fonts cannot encode a euro sign or a typographic minus. One project embeds Roboto specifically for this. If your labels can contain a currency symbol or a non-ASCII name, embed.
  • Lay out for a real page. A grid with cut marks on A4 and Letter, with margins inside any printer's unprintable area.
  • Codes must survive a photocopier. That means high error correction, generous quiet zones and a minimum module size — do not shrink to fit more per page.
  • PDF/A if it is an archival document. That brings an embedded colour profile and font-embedding requirements; only take that on if a regulation demands it.
Why generate the PDF on-device

It keeps a print flow working offline, it avoids sending an inventory of your physical space to a server, and it removes an entire backend surface. The only cost is that you write the layout code yourself, which for a grid of codes is an afternoon.

Payload design

Encode a reference, not a record — and treat every scanned payload as hostile input.

app://join?ws=abc123&t=8FKQ2M7XPD     ← good: opaque ids, short, deep-linkable
app://seat?id=a1b2c3                   ← good
{"workspace":"abc123","name":"…"}      ← bad: verbose, stale on read, no verification
RuleReason
Reference, do not embedA printed code containing data is stale the moment the data changes. An id is resolved fresh on every scan.
Use your deep-link schemeThe same payload then works from a camera app, a messaging app, or a printed sheet — one handler, three entry points.
Validate server-sideAnyone can generate a QR code containing any string. The scan is an input, never an authorisation.
Tokens are single-use and short-livedA photographed invite code used a week later is a credential leak. See device pairing.
Unambiguous alphabet for typeable codesExclude 0/O and 1/l/I. One project uses a 32-letter alphabet and a 10-character code so the QR always has a typed fallback.
Bound the length before parsingA scanner can return a very long string. Reject over a sane limit before doing anything with it.
Rule

Always provide a manual entry path next to the scanner. Cameras fail: no permission, a broken lens, a damaged code, a user on a device with no camera. A code the user can read aloud and type is the difference between a degraded experience and a blocked one — and it costs one text field.

Scanner UX

ElementBehaviour
PermissionRequested when the user taps scan, after a one-line explanation. Never at launch. See page 09.
Permanently deniedDetect it and offer a button that opens system settings — plus the manual entry field. Re-prompting does nothing and looks broken.
ReticleAn overlay showing where to aim. Users hold the phone too far away without one.
TorchA toggle. Codes are often scanned in badly-lit places.
Feedback on acceptHaptic plus a visual confirmation, immediately, before the async work resolves.
Unrecognised codeSay "this is not a valid X code" and keep scanning. Do not close the scanner on a wrong code.
LifecycleStop the camera when the route is backgrounded or popped. A live camera in the background drains battery and shows a privacy indicator.
Trap

Symptom: the camera stays on after leaving the scanner, or is black on return. The controller must be disposed on pop and re-created on push, and paused/resumed with the app lifecycle. Widget disposal alone is not enough — a route kept alive in a tab bar keeps the camera running. Hook AppLifecycleState as well as dispose.

When there is no code: OCR

Sometimes the value you need is printed on a receipt or lit on a display with no code anywhere. That is a different problem and a much harder one.

Text recognition: two engines, one per platform

On-device text recognition is mature: ML Kit on Android, Vision on iOS. One project uses Vision exclusively on iOS and strips the ML Kit pods from the IPA entirely with vendored dependency overrides — tens of megabytes of framework for code that never ran, because the plugin linked both platforms unconditionally.

Trap

Symptom: your iOS binary is far larger than expected. A cross-platform ML plugin links its full native stack on both platforms even if you only call it on one. If you use the platform's own engine on iOS, check whether the plugin still pulls the other one in — and if it does, vendor a copy with the unused platform removed. Remove the vendored fork when upstream offers a per-platform opt-out.

Seven-segment displays: label-anchored regions

Trap

Symptom: a text recogniser reads all the labels on a display and none of the numbers. General text recognisers are trained on typefaces. Seven-segment digits are disconnected line segments and read as nothing at all — while the printed words next to them ("VOLUME", "TOTAL", "PRICE") are recognised perfectly.

The failed approach: fixed template regions of interest per device model. It cannot work with a hand-held camera, because the display is never in the same place twice.

The approach that worked: use the general recogniser for what it is good at — finding the label boxes — and derive each value's region from the position of its label. A generous region below or beside "TOTAL" will contain the digits regardless of framing, and a dedicated segment decoder runs inside that region.

1. Run text recognition   → label boxes with positions
2. Match labels against a per-vendor anchor config
     { "label": "TOTAL", "anchor": "below", "widthFactor": 2.2, … }
3. Derive a value region from each matched label box
4. Run the seven-segment decoder INSIDE that region
5. Validate: plausible range, decimal places, cross-field arithmetic

Because the decoder segments within the derived region, the region only has to contain the digits — it can be generous. That is what makes the approach robust to a hand-held camera.

Rule

Ship a vendor configuration as data, not code, and let it be opt-in per layout. Anchor definitions in a JSON asset mean a new display layout is a data change. Keep a fixture corpus of real photographs and run the whole pipeline against it in tests — this is the recorded-fixture discipline from page 03, and OCR is where it matters most, because a synthetic rendering of a display is not a photograph of one.

Whatever the source, always show the user the parsed value in an editable field before committing it. OCR is a typing accelerator, not an authority. A wrong value silently accepted is worse than no OCR at all.
